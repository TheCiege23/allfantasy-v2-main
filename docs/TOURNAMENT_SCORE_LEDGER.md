# Opening tournament score ledger

Status: locked-setup foundation with owner review/finalization API. No HTTP ingestion route or active scheduler.

1. Complete and verify the opening draft, then prepare its legal rosters.
2. A future trusted schedule adapter maps a game to drafted player IDs and calls captureSeasonOpeningLineup before the frozen lock deadline. The service snapshots prepared starters and assigns the server timestamp. Retries of the same game are read-only; start-time/identity changes require audited schedule correction work.
3. A future trusted scorer fetches and reconciles provider data outside locks, calculates points under the frozen scoring contract, then calls ingestSeasonOpeningScores with a unique requestId, expectedRevision, period, source, observedAt, coverage and per-player score revisions. Full schedule coverage is an adapter attestation; the ledger cannot independently certify vendor completeness.
4. The service verifies database-derived bindings and stored lineups, computes the projected week, claims the completed draft session version and appends one digest-linked audit receipt atomically. Same-ID/same-content retries are safe. Same-ID/changed-content and conflicting revisions fail.
5. readSeasonOpeningScoreLedger validates all persisted revisions and lineup receipts before deriving missing/provisional/eligible status. It is an internal read and returns evidence-derived player identifiers; future owner routes must project safe counts and messages.

An eligible week is not finalized. No wins are inferred and no cut/bracket service consumes these receipts yet. The owner finalize command now binds review to the exact ledger revision/digest and rechecks correction closure in its atomic transaction. It saves a season_week_finalized_setup receipt and preserves prior revision history. A new score revision requires another review. Live activation must also replace the locked-setup gate through an audited, independently tested runtime path.

Internal stat-source refreshes now compare each complete current-period raw snapshot with the prior saved snapshot. Each ledger receipt includes source-content digests and counts of corrected/backfilled rows, status changes and advanced provider revisions. Removed old results, revision regressions, changed facts without a newer revision, and complete-coverage downgrades fail closed. A valid correction appends a new score revision and supersedes the old finalization until the owner reviews and finalizes again. These checks cannot attest that an external feed delivered its entire slate; the provider worker and exact-start source are still absent.

Storage uses existing TournamentAuditLog rows, deterministic primary keys and the existing tournament/action index. Snapshot/revision reads are capped at 251 rows to detect the 250-row limit; history is capped at 10,000 score rows. Before live rollout, certify query plans, payload sizes, retention and dedicated scoring storage if needed. A receipt digest is an integrity check, not authentication of arbitrary client/provider data or protection against a database administrator rewriting/truncating history.

Frozen setup lineups cannot change; this module does not implement daily edits, real-time cap enforcement, IR, trading, postponed-game rebinding or provider correction webhooks. See contracts/rolling-insights/GAPS.md N-01 before enabling correction-driven ingestion. No schema migration or production write was run for this batch.

Commissioner controls: /api/tournament/season-scoring accepts strict review/finalize commands only. Safe reports expose counts and an opaque token, never player evidence. The hub explicitly labels these as setup checkpoints; they cannot start scoring or advance teams. Future standings must validate that the finalization receipt still matches the newest score revision before using it.

Standings integration: reviewSeasonOpeningStandings and /api/tournament/season-standings read the complete frozen opening field through a selected opening week. A single read-only RepeatableRead snapshot verifies current ledger heads and finalization receipts. Superseded/unfinalized weeks are omitted from totals with explicit missing/checkpoint status. Full totals and ranks remain pending until every requested league/week is finalized. Unknown win outcomes stop the published tiebreaker sequence; no official seeds, cuts or bracket mutations are produced. The hub displays eight-team pages and league-week verification details. Query performance/isolation and a fully scored multi-league season remain unverified staging gates.

Fantasy matchup extension: captureSeasonOpeningMatchups is an internal trusted native-scheduler boundary. Publish explicit full-roster pairings before period start; never infer fantasy opponents from real-sport schedules. Pairing receipts are immutable and server-timestamped. Owner score finalization derives win/loss/tie outcomes atomically when those pairings exist. Each outcome binds the pairing digest, current ledger digest and finalization checkpoint. Exact score ties produce 0.5 win credit using the existing weekly-result contract. Corrections require re-finalization and fresh outcomes. Standings use verified credits only; a missing pairing/outcome remains unknown, not zero. Commissioner pairing controls, scheduler integration and audited schedule correction/backfill are still pending; no retrospective schedule is fabricated.
