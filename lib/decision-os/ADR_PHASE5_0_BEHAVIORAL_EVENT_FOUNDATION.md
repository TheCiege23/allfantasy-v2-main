# ADR Phase 5.0 — Behavioral Event Foundation

**Date:** 2026-06-30
**Status:** Accepted
**Author:** TheCiege23
**Phase:** 5.0 — Behavioral Event Foundation (prerequisite for Manager Intelligence, League
Intelligence, and Platform Intelligence)

---

## Context

Decision OS Phases 1–4 built the Canonical World substrate (read-only, origin-blind league
facts) and four decision slices (Lineup / Waiver / Trade / Commissioner Health) now running
at Stage 1 in production.

The next layer of intelligence requires a canonical behavioral record: *what managers
actually do in their leagues*. Lineup saves, trade proposals, waiver claims, commissioner
actions, draft picks, and engagement signals (viewing scoring, reading recaps) are all
observable facts that reveal manager behavior, league health, and platform engagement
patterns. Without a canonical model for these events, future intelligence features must
re-derive the same facts from raw DB tables in ad-hoc ways.

This ADR defines the **Behavioral Event Foundation** — the deterministic, provider-agnostic
event substrate that Manager Intelligence, League Intelligence, and Platform Intelligence
will consume.

---

## What This Is

A canonical event model. Each event represents a discrete thing a manager (or the system)
did in a league. Events carry:

- **What happened** (`eventType` from a finite, versioned taxonomy)
- **When** (`occurredAt`, `recordedAt` — distinguished to handle import lag)
- **Who** (`managerId` — null for system events)
- **Where** (`leagueId`)
- **How it was recorded** (`source`: `api` | `import` | `cron` | `system`)
- **Provenance** (which provider, which DB tables, when imported — metadata only, never decision inputs)
- **Typed metadata** (event-specific payload, per-type interfaces)
- **Completeness** (0–100 honest score — same pattern as Canonical World)
- **Uncertainty** (what is not known: timestamp confidence, actor confidence)

---

## What This Is Not

- **Not analytics** — no aggregation layer, no dashboards, no reporting.
- **Not AI** — no summarization, no prediction, no generation.
- **Not a new data store** — no new DB tables in Phase 5.0; events are constructed from
  existing rows (DB reads happen in Phase 5.1 ports).
- **Not a modification of Stage 1 slices** — completely additive; existing
  lineup/waiver/trade/commissioner slices are untouched.
- **Not a UI layer** — no components, no API routes.

---

## Principles

All three architecture principles from the Phase 1 freeze apply:

**P1 — Purpose-blindness:** Event shapes are provider-agnostic. A `trade_created` event
looks the same whether the league is imported from Sleeper or native AllFantasy. Provider
identity lives in `provenance.provider` only — never in the event type or metadata keys.

**P2 — Enrichment-as-truth / no fabrication:** Every nullable field (`managerId`,
`occurredAt`, per-metadata fields) is genuinely `null | undefined` when the value is
unknown. Completeness degrades honestly; no value is invented to fill a gap.

**P3 — AI governance:** This is a deterministic, read-only fact layer. AI systems MAY
consume behavioral events as input signals but MUST NOT generate or modify events. The
causal direction is one-way: events → intelligence, never intelligence → events.

## Event Taxonomy

### Roster events
| eventType | Trigger |
|-----------|---------|
| `lineup_viewed` | Manager opened the lineup editor |
| `lineup_saved` | Manager committed lineup changes |

### Transaction events
| eventType | Trigger |
|-----------|---------|
| `trade_created` | Trade proposal submitted |
| `trade_accepted` | Trade proposal accepted |
| `trade_rejected` | Trade proposal rejected or vetoed |
| `waiver_claim_created` | Waiver claim submitted |
| `waiver_claim_processed` | Waiver wire ran; claim awarded or denied |

### Commissioner events
| eventType | Trigger |
|-----------|---------|
| `commissioner_action` | Commissioner performed a hub action |
| `rules_changed` | League settings/rules modified |

### Engagement events
| eventType | Trigger |
|-----------|---------|
| `league_opened` | Manager opened the league (any surface) |
| `live_scoring_opened` | Manager opened live scoring view |
| `recap_viewed` | Manager viewed a week recap / matchup result |

### Draft events
| eventType | Trigger |
|-----------|---------|
| `draft_started` | Draft began |
| `draft_pick_made` | Draft pick made |

## Event Source Values

| source | Meaning |
|--------|---------|
| `api` | Recorded in real-time via an AllFantasy API call |
| `import` | Imported from a provider's historical data after the fact |
| `cron` | Generated by a scheduled job (e.g., waiver processing) |
| `system` | Generated by the AllFantasy platform itself (automated) |

---

## Completeness Model

Follows the same 0–100 integer pattern as `CanonicalWorld.dataCompleteness`:

| Score range | Meaning |
|-------------|---------|
| 80–100 | All fields present, timestamp is exact, actor confirmed |
| 60–79 | Minor gaps (e.g., player name but no player ID) |
| 40–59 | Significant gaps (e.g., actor inferred, not confirmed) |
| 0–39 | Minimal data; treat as signal-only, not ground truth |

Deduction guide (additive):
- `managerId` null → −20
- `occurredAt` approximate → −10
- `occurredAt` unknown → −30
- Provider metadata absent → −10
- Any required metadata field null → −10 per field

---

## Uncertainty Model

Two confidence axes:

**`timestampConfidence`**
- `'exact'` — `occurredAt` is the precise system time of the event
- `'approximate'` — `occurredAt` is derived (e.g., inferred from a related record's
  `createdAt`; may be off by seconds to hours)
- `'unknown'` — `occurredAt` is a best-guess or placeholder

**`actorConfidence`**
- `'confirmed'` — `managerId` is the authenticated user who performed the action
- `'inferred'` — `managerId` is derived (e.g., matched by roster ownership)
- `'unknown'` — actor cannot be determined (system events or import gaps)

---

## BehavioralFacts (derived from events)

Phase 5.0 defines the fact interface shapes. Assembly logic (reading from DB → constructing
events → assembling facts) is Phase 5.1.

**`ManagerBehavioralFacts`** — per-manager behavioral state within a league:
- Last lineup save, activity counts (lineup saves, trades, waivers, commissioner actions)
- Engagement signals (league opens, live scoring sessions, recap views, draft picks)
- Completeness, event count, lookback window

**`LeagueBehavioralFacts`** — league-level behavioral state:
- Aggregated transaction counts (trades, waivers, commissioner actions, rules changes)
- Active manager IDs, last activity event, draft history
- Completeness, manager count, lookback window

## Architecture

### Directory

```
lib/decision-os/behavioral/
  events/
    types.ts        Interfaces: per-event metadata, discriminated union, provenance, uncertainty
    taxonomy.ts     Constants: BEHAVIORAL_EVENT_TYPES, categories, labels, sources, type guard
  facts.ts          Interfaces: ManagerBehavioralFacts, LeagueBehavioralFacts, completeness
  index.ts          Barrel export
```

### What is NOT in Phase 5.0

- `port.ts` — DB reads (Phase 5.1)
- `assemble.ts` — event assembly from raw rows (Phase 5.1)
- `shadow.ts` — shadow runner (Phase 5.2+)
- API routes, components (out of scope)

### Relationship to existing Decision OS layers

```
lib/decision-os/world/          ← League/roster/team facts (origin-blind)
lib/decision-os/behavioral/     ← Behavioral events (NEW, Phase 5.0)
  └── feeds →
    lib/decision-os/lineup/         ← Lineup decisions (Stage 1)
    lib/decision-os/waiver/         ← Waiver decisions (Stage 1)
    lib/decision-os/trade/          ← Trade decisions (Stage 1)
    lib/decision-os/commissioner-health/  ← Health decisions (Stage 1)
    [future] manager-intelligence/
    [future] league-intelligence/
    [future] platform-intelligence/
```

The behavioral layer is a peer of the world layer, not a dependent. Neither reads from the
other in Phase 5.0.

---

## Invariants

1. No event type will be added or removed without a new ADR.
2. Per-event metadata interfaces are additive (new optional fields only; never remove).
3. `completeness` is always in [0, 100].
4. `managerId` is always nullable — system events exist.
5. `provenance.provider` is null for system/native events; non-null means import origin.
6. No event carries provider-specific key names in its metadata.
7. This layer makes no writes and requires no DB connection in Phase 5.0.

## Test Coverage

`__tests__/decision-os/behavioral-event-schema.test.ts` verifies:
- Taxonomy exhaustiveness (all 14 types present)
- Category completeness (every type in exactly one category)
- Label completeness (every type has a human label)
- Source list completeness
- `getEventCategory` returns the correct category for every type
- `isBehavioralEvent` type guard accepts valid events and rejects invalid shapes
- Completeness is bounded 0–100 by `clampCompleteness`
- `makeEmptyProvenance` and `makeMaxUncertainty` helpers produce valid values
- Named event shapes satisfy TypeScript's discriminated union (compile-time)
